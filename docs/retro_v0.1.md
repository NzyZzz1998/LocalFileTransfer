## 版本结论

v0.1 是一次成功的本地 MVP：核心链路已经从需求、实现、自动化、单文件构建走到两台物理设备的真实传输。它证明了“发送端启动一个本地服务、两端只用浏览器、文件可经 WebRTC 在局域网传输”可行。

v0.1 还不是稳定的跨系统快传版本。当前证据不能证明 TUN/VPN 环境兼容、跨操作系统兼容、大文件能力或实际吞吐；对外仍只应称为本地 MVP。

## 做得好的地方

- 产品边界清楚：局域网、纯浏览器、单发单收、无账号、无云盘。
- 两次人工确认落实为协议不变量：发送方批准前不协商，接收方批准清单前不发送文件字节。
- v0.1 的实现与隐私声明一致：信令服务没有文件上传或持久化接口，直连失败不会静默中转。
- 房间白名单、Origin、安全头、限速、容量、分块、背压、取消、断连与字节一致性均有自动化证据。
- 文档明确区分同机 E2E、物理设备和跨系统验证，没有把推断写成完成。
- 源码、测试、README、Git 历史和 `v0.1.0` 标签已经形成可回退基线。

## 暴露的问题与根因

| ID | 问题 | 根因判断 | 影响 |
| --- | --- | --- | --- |
| R-P01 | 用户不知道该访问哪个地址 | 服务只打印 `0.0.0.0:3000`，没有筛选并展示真实 LAN 地址 | 首次成功时间变长 |
| R-P02 | “等待/很慢”与“无法连接”难区分 | UI 没有把信令、人工批准、ICE、DataChannel 拆成可观察阶段，也没有显式建连截止 | 用户只能等待或猜测 |
| R-P03 | TUN 开启时失败提示不可行动 | 直连失败统一收口为通用断连文案；浏览器也不能可靠绑定物理网卡 | 需要用户自行排查代理 |
| R-P04 | “快传”缺乏证据 | 没有接收确认速率、ETA、性能基线或大文件真机样本 | 无法判断瓶颈在建连还是吞吐 |
| R-P05 | LAN HTTP 下大文件能力受限 | OPFS 属于安全上下文能力，当前真实 LAN Chrome 会退回 256 MiB 单文件内存存储；批次总量未预检 | 大文件可能在用户确认后才失败 |
| R-P06 | 传输会继承建房 TTL | 房间定位有效期与已配对会话生命周期未分离 | 长传输可能被意外终止 |
| R-P07 | 跨系统仍是架构推断 | 真机 OS/浏览器矩阵尚未执行 | 不能发布“跨系统已验证”声明 |

## 关键学习

1. 用户的核心结果不是“WebRTC 成功”，而是两台电脑第一次尝试就能把文件送达。
2. “似乎不快”本次实际发生在建连阶段，不能据此判断文件吞吐慢；下一版必须把连接耗时与传输速度分开。
3. VPN/TUN、访客网络和防火墙不是边缘环境，应成为局域网工具的标准失败场景。
4. “文件不经过本地服务”是 v0.1 的架构决策，不是用户原始需求的同义词；改变它必须重新确认并在 UI 中明确展示。
5. 浏览器零安装降低了接收门槛，也带来了 LAN HTTP 安全上下文和落盘能力限制，不能只靠同机 loopback E2E 判断。

## 承重假设回写

- `H-001`（无 TURN 的局域网候选覆盖目标网络）：部分支持。TUN 关闭时成功；TUN 开启时反证成立。v0.2 必须至少提供可行动诊断，是否增加本地中转由 `V2-G01` 决定。
- `H-002`（浏览器暂存后保存可接受）：待补证。真实 LAN Chrome 已确认会退回内存，但还没有真实大文件任务数据。
- `H-003`（一台电脑启动本地站点符合使用预期）：部分支持。用户完成了运行与访问，但查 IP 是明确摩擦。

## 版本停止边界

v0.1 保持冻结：不修改 `v0.1.0` 标签，不回填新功能，不把后续验证写成标签时已经具备。所有改进进入 `dev/v0.2`；跨系统、速度和大文件结论在取得新证据前继续标记“待验证”。
