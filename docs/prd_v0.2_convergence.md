# 渡口 v0.2 方案收敛：可靠传输版

## 追踪信息

- 交付模式：Vibe Coding 全流程型
- PRD 类型：方案收敛版，不是完整 PRD
- 当前阶段：v0.1 已复盘；F1～F7 已确认，已进入完整 PRD 与开发承接
- 目标版本：v0.2
- 上游来源：`docs/retro_v0.1.md`
- 当前分支：`test`（2026-09-05 按用户指定同步；本文仍为历史方案，实施状态见 progress）
- 进入开发授权：已获得（用户于 2026-09-04 表示“开始迭代”）
- 最后更新：2026-09-04

## 当前阶段判断

产品仍处于验证期。v0.1 已完成 L2 自动化与一组双真机成功，但跨系统、TUN 兼容、吞吐和大文件仍缺真实证据。v0.2 应先降低首次连接失败和不可解释等待，不扩张到文件夹、历史或云端。

## 新增决策

- `V2-D01`（来源已确认）：用户希望 TUN 开启时仍能传输，并批准在 WebRTC 直连失败后提供本地中转路线。
- `V2-D02`（来源已确认）：v0.2 不应只交付一项孤立功能，需要形成完整、可感知的版本升级。
- `V2-D03`（风险推导要求）：本地中转必须由用户明确选择、不得落盘、不得静默切换；文件路径和保护强度必须如实展示。
- `V2-D04`（来源已确认）：跨系统是产品原始要求，v0.2 必须将 Windows、macOS、Linux 从架构推断推进到可下载产物与实际验证。

## 已确认事实

- 用户仍需要开启 JiuX TUN 使用 GPT；关闭 TUN 后渡口真机传输成功。
- 页面与 WebSocket 信令在 TUN 开启时可用，WebRTC 直连失败。
- 当前浏览器 API 无法可靠要求 WebRTC 只使用某张物理网卡；候选过滤只能尽力优化，不能承诺根治 TUN。
- v0.1 承诺文件清单与内容不经过信令服务，且不静默中转。
- 真实 LAN HTTP 下的当前 Windows Chrome 没有 OPFS，接收端会使用 256 MiB 单文件内存兜底。

## 版本目标

版本主题：**开着 TUN 也能传，失败不靠猜，长传输不半路断。**

让用户无需查询网络命令即可开始连接，清楚知道“现在卡在哪、该做什么、传得有多快”；直连不可用时可明确选择受控的本地中转，同时修正会中断长传输的生命周期和存储预检问题。

## 互斥方案

| 方案 | 用户结果 | 成本与风险 | 验证方式 | 判断 |
| --- | --- | --- | --- | --- |
| S1 仅诊断引导 | 失败能看懂，但 TUN 开启时仍需用户改设置或关闭 TUN | 成本最低；不解决当前故障 | 当前双真机分别在 TUN 开/关重测 | 适合 v0.1.1，不足以支撑 v0.2 |
| S2 只做 WebRTC 调优 | 保持纯直连，可能改善部分候选与吞吐问题 | 浏览器不能可靠绑定网卡；mDNS、虚拟网卡和跨浏览器差异可能让规则失效 | 多浏览器、TUN 与多网卡故障注入 | 作为辅助优化，不作为 TUN 解法 |
| S3 直连优先 + 显式本地中转 | 直连失败后，用户可选择经“运行渡口的电脑”继续传输 | 改变文件路径与隐私说明；必须新增授权、背压、容量和安全合同 | 强制直连失败 E2E + 当前 JiuX TUN 真机 | 已确认采用（`V2-D01`） |

采用 S3 的理由：它是三个方案中唯一直接覆盖当前 TUN 故障、又不要求用户修改代理设置的路径。S1 的诊断能力继续作为配套；S2 中的性能优化只有在真机基线证明必要后才实施，不能替代本地中转。

## 建议版本功能包

### F1：一眼就能连接

- `V2-P01`：启动时展示可访问的 LAN IPv4 地址，而不是只显示 `0.0.0.0`；提供复制访问地址和二维码入口。虚拟网卡与候选地址必须可解释，不能声称自动选中地址一定可达。

### F2：直连失败也能继续

- `V2-R01`：只在直连失败且尚未发送文件字节时展示“改用本地中转”；禁止静默回退和传输中途切换。
- `V2-R02`：双方分别看到并确认路径变化，页面持续标记“本地中转”，不得继续显示“浏览器直连”。
- `V2-R03`：中转通道与信令通道隔离，使用一次性、房间与角色绑定的高熵凭据；发送方批准和接收方清单确认仍是前置条件。
- `V2-R04`：服务端不落盘，队列与内存有硬上限，慢接收端触发端到端背压；取消、掉线和超限必须释放资源。
- `V2-R05`：中转的清单、控制帧和文件块使用应用层加密与完整性保护，服务端只转发不透明数据。由于 LAN HTTP 的可信边界弱于 WebRTC DTLS，完整 PRD 必须限制安全声明，不能宣称两者等价。

### F3：连接失败不靠猜

- `V2-P02`：双端连接时间线拆分为配对站、等待发送方批准、寻找局域网路线、验证通道、可以传输。
- `V2-P03`：连接阶段有显式截止、原地重试和分类错误；VPN/TUN、访客 Wi-Fi、防火墙只作为常见原因提示，不伪装成已被浏览器检测。
- `V2-P04`：诊断副本只包含版本、阶段、耗时、WebSocket/ICE/连接状态与候选类型；不得包含房间码、IP、SDP、文件名或文件内容。
- `V2-P08`：保留发送方已选文件，连接失败后可一键生成新码重试。

### F4：速度真正可见

- `V2-P07`：进度区分“发送队列字节”和“接收方已确认字节”；显示基于确认字节的当前速度、平均速度、已用时间与预计剩余。
- `V2-P09`：先建立真机吞吐基线，再调整分块、水位与 UI 刷新频率；没有基线前不承诺具体加速比例。

### F5：长传输不中途失效

- `V2-P05`：等待加入的房间保持 10 分钟有效；完成配对后不再受建房绝对 TTL 终止，改由存活状态和显式断连控制。
- `V2-P10`：直连和本地中转共用明确的存活、取消、断连清理与资源上限合同。

### F6：接收前就知道能不能存

- `V2-P06`：接收清单阶段预检当前存储能力与批次总容量；内存模式明确展示 256 MiB 单文件限制，超限时在零文件字节前阻止接收，批次总限制在完整 PRD 中锁定。

### F7：跨系统可运行、可验证

- 运行渡口服务的电脑提供 Windows x64、macOS Apple Silicon / Intel、Linux x64 对应的独立可执行产物；接收电脑仍只需浏览器。
- 以桌面端稳定版 Chrome/Chromium（包含 Edge）为 v0.2 跨系统基线；Safari、Firefox 的完整跨引擎兼容矩阵继续作为后续验证，不冒充已支持。
- Windows ↔ macOS、Windows ↔ Linux、macOS ↔ Linux 三组均记录双向直连结果；本地中转至少覆盖实际可取得设备上的一组 TUN 失败场景。缺少真机时标记“待补证”，不能用构建成功替代运行成功。
- 自动化分别验证各系统产物能够启动、返回健康检查并提供完整网页；文件名覆盖中文、空格与常见 Unicode 字符。
- 未签名产物的 Windows SmartScreen、macOS Gatekeeper 与 Linux 执行权限处理写入使用说明；代码签名与商店分发不进入 v0.2。
- 创建 Release、上传产物和推送远端仍需单独授权。

### 延后

- 文件夹、断点续传、传输历史、群发、设备自动发现、账号、云端、公网部署。
- 自动修改 VPN/TUN 配置。
- 大于 256 MiB 的浏览器落盘方案；它需要与本地中转、原生下载流或 HTTPS 安全上下文一起做独立架构决策。
- Safari、Firefox 的完整跨引擎组合矩阵；v0.2 的跨系统基线先锁定 Chrome/Chromium（包含 Edge）。

## 开发前验收骨架

- 现有 91 项自动化与 direct E2E 必须保持通过。
- 新增连接阶段、超时、重试、TTL 分离、存储预检、确认字节速度的确定性测试。
- TUN 关闭：现有双真机直连仍成功。
- TUN 开启且未配置 LAN bypass：在明确截止内给出可操作提示；用户确认本地中转后可完成传输。
- 成功传输的文件必须逐字节一致；双方批准前仍为零文件字节。
- 跨系统、速度和大文件结论只按实际设备、浏览器、方向、文件大小和证据记录，不从架构推断。
