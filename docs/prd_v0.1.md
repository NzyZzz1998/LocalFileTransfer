- 上游来源：本任务 `/idea` 结论及用户对“纯浏览器方案”的确认

## 已确认事实与解释

- F-001：用于多台电脑间传文件。
- F-002：只做局域网一次性快传。
- F-003：需要跨系统。
- F-004：两端都只打开网页，不要求安装客户端。
- F-005：交付模式为 `vibe_coding`。
- D-001：两端访问同一个站点；本地 MVP 由局域网内一台电脑通过 HTTP 提供页面与信令。轻量信令服务只帮助浏览器建立连接，文件名和文件内容通过 WebRTC DataChannel 点对点传输，不经过信令服务。
- D-002：v0.1 不配置 TURN 中继，只使用直连候选；直连失败时明确失败，不把文件回退到服务器。
- A-001（N4 建议默认）：支持 Windows、macOS、Linux 上的最新 Chrome、Edge、Firefox、Safari；具体版本在真机验收后锁定。
- A-002（N4 建议默认）：建立房间需要访问网站；文件传输目标为同一可互访局域网。

## 目标与非目标

目标：发送方选择文件并生成 6 位接收码，接收方输入接收码、双方确认后，在浏览器间加密直传；全过程能看见连接、文件与进度状态，失败不会悄悄改走云端。

本次包含：单发送方与单接收方、多个普通文件、拖放选择、房间码、连接确认、文件清单确认、可靠有序分块、背压、逐文件和总体进度、取消、完成后用户主动保存、房间过期与断连恢复提示。

延后：文件夹、断点续传、传输历史、设备自动发现、保存目录直写、二维码、PWA 离线壳。

不做：账号、云盘、文件服务器落盘、TURN/中继传输、公网跨网传输、群发、同步、预览、自动打开文件、恶意软件扫描。

## 核心流程

1. 两台电脑访问同一网页，分别选择“发送文件”或“接收文件”。
2. 发送方选择文件后创建房间，信令服务返回 6 位接收码；房间仅短时有效。
3. 接收方输入接收码并请求加入；发送方看到一台设备请求连接，明确允许或拒绝。
4. 允许后，双方通过信令交换 WebRTC 连接信息；建立 DTLS 加密的 DataChannel。信令服务不接收文件清单或内容。
5. 发送方经 DataChannel 提交文件清单；接收方明确接收或拒绝。
6. 接收后逐文件分块发送。发送方依据 `bufferedAmount` 背压，接收方按序写入浏览器暂存区；双方显示进度。
7. 文件字节数一致后标记已接收；接收方逐个点击保存。所有文件处理完毕后关闭房间。

## 状态合同

- 房间：`idle -> creating -> waiting_peer -> join_pending -> connecting -> connected -> closed | expired | failed`。
- 批次：`draft -> offering -> awaiting_acceptance -> transferring -> completed | rejected | cancelled | failed`。
- 文件：`pending -> transferring -> received -> saved | cancelled | failed`。
- 终态不可回退；取消幂等；任一端离开后不得让第三台电脑接管原房间。

业务不变量：发送方批准连接前不交换 WebRTC offer；接收方批准清单前不发送文件字节；信令服务不得接收清单或文件内容；不配置中继时直连失败必须如实失败；接收内容默认不执行、不预览。

## 文件传输协议

- WebRTC DataChannel 使用可靠、有序模式。
- 控制帧为有版本号的 JSON，至少包括 `offer_manifest`、`accept_manifest`、`reject_manifest`、`file_start`、`file_end`、`file_received`、`cancel`、`transfer_complete`、`error`。
- 二进制帧只属于当前 `file_start` 声明的文件；文件按顺序传输，v0.1 不并行。
- 分块大小不超过双方协商的 `RTCSctpTransport.maxMessageSize`，默认上限 64 KiB；缓存超过高水位暂停，降至低水位继续。
- 每个文件校验实际接收字节数；WebRTC 的可靠有序传输与 DTLS 提供链路完整性。独立内容摘要延后。
- 接收端优先使用 Origin Private File System 流式暂存；不支持时降级到内存并展示容量限制。完成后通过用户点击触发浏览器下载。

## 信令服务合同

- 仅保存内存态房间，不使用数据库；重启后房间失效。
- 每个房间仅一发一收。接收方加入先进入 `join_pending`，必须由发送方批准。
- WebSocket 消息白名单：`create_room`、`join_room`、`approve_join`、`reject_join`、`signal`、`leave`、`ping`。
- `signal` 只允许转发 WebRTC `offer`、`answer`、`candidate`，限制消息大小；其他类型拒绝。
- 6 位接收码只是定位房间，不能替代发送方批准；加入尝试按来源地址限速。
- 房间过期、任一端断连或主动离开时清理，并通知仍在线的一方。
- 本地 MVP 校验 WebSocket `Origin`、不开放跨域，所有页面资源自托管。未来若进入公网部署，必须在 HTTPS/WSS 下运行并单独验收 TLS 终止反向代理与 Origin 适配。

## 隐私与安全边界

- WebRTC DataChannel 使用 DTLS 加密，但信令服务仍能看到连接时间、房间码、IP/网络元数据和 SDP/ICE 信息。
- v0.1 信任所部署的信令服务；不宣称对恶意信令服务提供端到端身份验证。
- 页面设置 CSP、`nosniff`、`no-referrer`、禁止嵌入与最小 Permissions Policy。
- 文件名仅用 `textContent` 渲染；不将接收文件注入页面、不自动预览。
- 房间码错误、已满、过期分别给可恢复提示，但不泄露其他房间信息。

## UI 与命令结果

- 首页只保留“发送文件”“接收文件”两个对等入口，并持续显示“文件点对点直传，服务端不保存”。
- 发送页按“选文件—生成码—允许设备—传输”呈现；接收页按“输码—等待允许—确认清单—保存”呈现。
- 返回首页：传输前直接退出；已有房间或传输中先确认，确认后通知对端并清理本地状态。
- 取消：等待或传输中均可执行；重复取消保持原终态。
- 保存：仅对 `received` 文件可用；失败时保留暂存并允许再次点击。

## 原型交付门禁

设计方向为“渡口调度票据”：暖纸色、深墨色、信号橙和航道绿；大号接收码像站台翻牌，连接路径像航线，不使用云盘式通用面板。

| 原型交付门禁 | 本轮要求 |
| --- | --- |
| 交付文件 | `src/web/index.html`、`src/web/app.css`、`src/web/app.js`；本轮不以低保真线框替代 |
| 状态与出口 | 覆盖正常、空、错、禁用、加载及允许、拒绝、接收、取消、返回、保存 |
| 模拟边界 | `?demo=sender` 与 `?demo=receiver` 为模拟信令和传输；不证明真实 WebRTC 或跨系统能力 |
| 浏览器验证 | 真实 Chromium 检查桌面/窄屏、关键交互、控制台及页面脚本错误 |
| 结论回写 | 结果回写本节和 `progress_v0.1.md`；保护双向确认、文件不经服务端和失败不降级中继 |

## 验收与门禁

- L0：状态、安全、信令白名单和范围静态检查。
- L1：高保真原型双视口及关键路径预检。
- L2：两个真实浏览器上下文完成房间创建、加入、双向确认和文件下载；房间/限速单元测试；服务构建检查。
- L3：Windows↔macOS、Windows↔Linux、macOS↔Linux 的真实局域网互传，阻塞公开 Beta，不阻塞本地 MVP。
- 进入开发授权：已获得（用户明确选择 Vibe Coding，并确认纯浏览器方向）。

P0 通过标准：未批准连接时不建立对等通道；未批准清单时零文件字节；成功文件逐字节一致；信令服务代码不存在文件上传或文件持久化路径；取消和断连终止传输；所有实际传输使用 `relay` 之外的 ICE 候选；桌面与窄屏主路径无脚本错误。

L2 结论（2026-09-04）：通过。Bun 全量 91 个测试通过；两个隔离 Chromium 上下文从最新 Windows 单文件构建完成真实房间、双向确认、已知非中继路线认证、65,537 字节下载一致性、未保存退出确认与 OPFS 离页清理。此结论不替代 L3 三平台真机互传。

## 承重假设

- H-001：无 TURN 的局域网候选能覆盖目标网络。使用三组异构系统实测；任一常见网络持续无法直连时，优先改进诊断，不静默增加中继。
- H-002：浏览器暂存后再保存可接受。记录 10 次自用任务；若至少 3 次因容量或保存步骤失败，则将直接保存能力前移。该 N4 阈值确认前不是正式业务门禁。
- H-003：在局域网一台电脑启动本地站点、其他电脑用浏览器访问符合“局域网快传”的理解；若用户要求完全不启动本地服务，则另开桌面壳/PWA 方案，不混入 v0.1。
